# PR size: a reviewable-lines count, size guidance in feature-loop, a warning in review and CI

## Goal

Keep each pull request small enough to review well (#20). Agents get a number to check before
pushing, guidance on how to split work, and a warning from `agent-review` and CI when a
branch is too big. Nothing blocks a push or a merge: some changes cannot be split.

Why: pactling PRs of 4,622 to 9,794 added lines each got one review pass, with the owner's skim
as the only real check (#20). On PR #27, a 1,300-line diff passed PR-Agent's 32,000-token
prompt cap, and later reviews silently left out `test.yml`, `.pr_agent.toml` and the review
skill itself.

## Probed facts (git 2.43.0, 2026-11-02, a disposable repository)

All verified against the real system:

- `git diff --numstat BASE HEAD` prints `added<TAB>deleted<TAB>path`; a binary file is `-	-`;
  a pure rename (renames are on by default) is `0	0	old => new`, so a rename counts nothing.
- Pathspec magic excludes paths inside git: `-- . ':(exclude,glob)**/fixtures/**'` dropped a
  fixture; `':(exclude,glob)**/Cargo.lock'` dropped a lockfile in any directory.
- `':(exclude,attr:linguist-generated)'` drops a file marked `linguist-generated` (value
  "set") but NOT one marked `linguist-generated=true` (value "true"), which is the form
  GitHub documents. `':(exclude,attr:linguist-generated=true)'` drops that one. Both are needed.
- `git diff BASE...HEAD` (three dots) diffs from the merge base, the PR's own changes.

## Decisions

1. **Measure added lines, excluding generated files.** Deleted lines are cheap to review and
   #20's evidence is in added lines. Excluded by default: lockfiles (`Cargo.lock`,
   `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `poetry.lock`, `uv.lock`,
   `Gemfile.lock`, `go.sum`, `composer.lock`), `fixtures/`, `captures/`, `testdata/`,
   `__snapshots__/`, `*.snap`, and files marked `linguist-generated` in `.gitattributes`.
   A repository adds its own with `git config --add prsize.exclude '<glob>'`.
   Rejected: counting every line (a regenerated lockfile would trip it), or added plus
   deleted (a deletion-only cleanup would look big).
2. **Aim at 400, split above 1,000**, settable with `git config prsize.aim` and
   `prsize.stop`, or `--aim` and `--stop`. 400 follows the commonly cited point where review
   effectiveness falls off; 1,000 sits below the 1,300 lines that already overflowed
   PR-Agent's cap on #27. Rejected: #20's 1,500, which #27 shows is too high.
3. **A new command, `bin/pr-size`,** so agents, `agent-review` and CI share one count. Exit 0
   whatever the size, unless `--fail` asks for exit 1 above the stop limit. Above the stop
   limit it lists added lines per commit, to show where to split. `--github` also writes a
   `::warning::` and a step-summary table. Rejected: counting inside `agent-review` alone,
   which CI and the skill could not reuse.
4. **Warn, never block.** `agent-review code` prints the warning on stderr, so the review's
   stdout is unchanged, and suggests reviewing per commit range. CI runs `pr-size --github` and
   stays green. Rejected: a failing check, because a migration or a generated API client
   legitimately cannot be split; the owner decides.
5. **The guidance lives in feature-loop**, where agents plan and finish work: step 2 sizes the
   task list, step 7 runs `pr-size` before pushing, and a new section says how to split.
   Rejected: a new rule in `AGENT-WORKFLOW.md`, which every session loads; the loop is where
   the decision is made.

## Tasks

1. `bin/pr-size.test.sh`, tests: "counts added lines of a branch since its merge base",
   "skips lockfiles, fixtures and captures", "skips linguist-generated files in both forms",
   "a pure rename and a binary count nothing", "prsize.exclude adds globs", "says under aim,
   over aim, and split above stop", "lists per-commit counts above stop", "--fail exits 1
   only above stop", "--github writes a warning annotation and a summary", "aim and stop come
   from git config or flags", "rejects a bad range or option". Then `bin/pr-size`.
2. `bin/agent-review.test.sh`: "a branch above the stop limit gets a size warning on stderr,
   and the review still runs"; "a small branch gets none". Then `bin/agent-review`.
3. `install.sh` links `~/.local/bin/pr-size`; `install.test.sh` checks the link.
4. `.github/workflows/test.yml`: a `pr size` job on pull requests (`fetch-depth: 0`); the
   `pr-size` suite in the test job.
5. `skills/feature-loop/SKILL.md`: step 2, step 7, a "Keep pull requests reviewable"
   section, two rationalization rows. `README.md`: the command.

## Checking

The suites above, red first; mutation-check each guard in `pr-size` and the warning in
`agent-review`. Use it as its user would: run `pr-size` on this branch, on PR #27's branch
(about 1,300 lines, expect the split message), and with a bad range. Independent review by a
model family other than the author's.
