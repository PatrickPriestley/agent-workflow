# A record's frontmatter names its tasks, and `dispatch` hands each to a fresh agent session

## Goal

Each task of an approved tier 2 record is built by a separate agent session that gets the
record, not the conversation: the record's frontmatter lists the tasks and the plugin to load,
and one command cuts a branch for the next task, runs the agent in it with the plugin
installed, checks the result the way CI would, and pushes the branch. The gate the skill
describes (approved before code, one task after another) is something the command enforces,
not something the controller remembers.

## Probed facts

- Verified against the real system (git 2.x here, 2026-11-08): `git worktree add -B
  <branch> <dir> origin/main` cuts a branch in a sibling directory; the worktree shares the
  repository's config (`user.name`, `redcheck.run`); `git push -u origin <branch>` to a bare
  remote works; `git ls-remote --heads` lists the branches there. After a squash merge and
  branch deletion, `git merge-base --is-ancestor` says the branch is not an ancestor of main,
  so "has this task merged" cannot be read from history alone.
- Verified against the real system (Claude Code 2.1.319, 2026-11-08): `claude -p
  --permission-mode acceptEdits --output-format json < brief.md` takes the prompt on stdin
  and returns `type`, `subtype`, `is_error`, `num_turns`, `total_cost_usd`, `duration_ms`
  and `result`; with `--plugin-dir plugins/change-record` the session lists the
  `change-record:change` skill (probed for the outcome-evals record).
- Verified against the real system (Claude Code 2.1.319, 2026-11-08, this environment): a
  `claude -p --permission-mode acceptEdits` session in a worktree wrote the code and tests for
  a toy task but was denied every `python3` and `git add`/`git commit` call (24 denials in the
  result's `permission_denials`, 39 turns, 1.55 USD) and so made no commits; the same mode
  with `--allowedTools Bash` runs them.
- Exact source: `bin/record-check` reads `id`, `tier` and `status` from the frontmatter by
  name (`field()`) and ignores other keys, so `plugin:` and `tasks:` can be added without
  changing it; a code PR may change other frontmatter lines as long as tier and status obey
  its rules.
- Exact source: `skills/incident-to-eval/scripts/run-eval.sh` runs the agent with the prompt
  from a file and `--permission-mode acceptEdits`, and keeps the agent's JSON beside the
  sandbox as `<dir>.agent.json`; `dispatch` copies that layout.

## Decisions

- A task counts as merged when the record on the base branch carries `done: true` under
  that task, a line `dispatch` itself commits on the task's branch after the agent finishes,
  so it reads true on main only once that branch has merged. Rejected: `git merge-base
  --is-ancestor`, which squash merges defeat; and the remote branch's absence, which cannot
  tell "merged" from "never started".
- The frontmatter tasks map to the numbered items under `## Tasks` by position; the brief
  quotes the matching item, and a task with no item of its own fails before the agent runs.
  Rejected: a `section:` field with a heading anchor per task, which is a second thing to
  keep in step with the prose; and (after review) falling back to the whole Tasks section,
  which briefs one session with every task's work.
- The brief is generated from the record (title, Goal, Probed facts, Decisions, the one task
  item, Checks) plus fixed instructions: use the existing record, do not change its tier or
  status, commit but do not push, end with the PR description whose first line is the
  `Change:` line. Rejected: handing the agent the controller's conversation, which is what
  the record is meant to replace.
- `dispatch` pushes only when `record-check` passes and `red-check` does not fail, and leaves
  the worktree in place either way so a failed run can be inspected. Rejected: pushing
  whatever the agent produced and letting CI refuse it, which spends a review on a branch the
  checks already rejected.
- The default agent command allows the Bash tool outright (`--allowedTools Bash`) beside
  `acceptEdits`, and the summary reports any command still denied. Rejected: `acceptEdits`
  alone, which the real run showed denies every test run and commit, so the agent cannot
  follow the skill's loop; and `--dangerously-skip-permissions`, which is wider than the
  worktree needs.
- A kept worktree from a failed attempt, or a local task branch with commits beyond the
  base whose worktree is gone (a reboot empties the default worktree root under `/tmp`), is
  never discarded by a later run unless `--fresh` is passed; the task fails with the path or
  branch instead. Rejected (after review, twice): starting over silently, which destroys the
  unpushed commits the README said were kept for inspection.
- The `done` marker is verified after it is written and the task fails if it is absent, and
  task names are compared with trailing comments stripped, as the parser strips them.
  Rejected (after review): trusting the edit, which pushed a branch without the marker when
  the task line carried a comment, and would have left every `after` gate closed for good.
- `--agent CMD` replaces the whole agent command, so the tests drive a fake agent that applies
  a canned change and prints the same JSON. Rejected: a fake `claude` on PATH, which hides
  what is being substituted.
- The default run advances the pipeline: each task in order is skipped if its branch is
  already on the remote, stops the run if its `after` task is not yet done on the base, and
  otherwise runs. `--task NAME` runs one task, still behind its gate, and only a name the
  record lacks is refused. An `after:` that names no task, or a task listed later, is refused
  before anything runs (after review: either would otherwise read as a wait that never ends).
  Task names must be plain slugs and worktrees live under `<worktrees>/<id>/`, since a name
  is a directory (after review: `..` in a name plus `--fresh` reached `rm -rf` outside the
  root, and two records sharing a task name shared one directory). A tasks entry without a
  name, or any line under `tasks:` outside the grammar (an entry `- name: <slug>` and its
  `branch`, `after` and `done` fields), is refused with the line quoted rather than dropped
  (after review, twice: a dropped entry shifted the ones after it onto the wrong numbered
  items, a wrong build that read as success; and a counter that did not strip comments
  refused the template's own `tasks:   # optional` line, and the done-marker writer did not
  read that line either, so the marker was never set after the agent had run). Task names
  must be unique, and so must the branches they resolve to, since the in-flight skip and the
  `--fresh` cleanup key on the branch, and no task branch may be the base branch (after
  review: a duplicate name, then a duplicate branch, then the base branch itself, each read
  as in flight and was silently skipped). A relative `--worktrees`
  path is taken from the caller's directory and made absolute, since the checks run after a
  `cd` into the worktree (after review: a relative root made every check fail after the agent
  had already run). Rejected: running every
  task at once in parallel worktrees, which the `after` field exists to prevent.

## Checks

`bash plugins/change-record/bin/dispatch.test.sh`. Real use: in a scratch repository with a
toy tier 2 record approved on main and one task, `dispatch docs/changes/<id>.md` with the real
agent cuts the branch, runs the session with the plugin, and pushes; the error path is
`dispatch docs/changes/2026-11-08-outcome-evals.md` in this repository, which must refuse
because that record is not approved on main. The independent reviewer should attack: whether
a task can run before its `after` task has merged; whether a failed check can still push;
whether the brief leaks anything outside the record; and whether the `done` line can be set
on the wrong task.

## Outcome

Reviewed by: pr-agent openai/glm-5.3 (the repository's CI review on the pull request; its
findings are the "after review" corrections in Decisions, each fixed red-first).

Shipped: `plugins/change-record/bin/dispatch` and its suite (`dispatch.test.sh`, 214
assertions over a bare remote and fake agents), the optional `plugin:` and `tasks:`
frontmatter in both templates and the skill's references, the README section and the CI step.
Every guard was broken by hand in turn and a test failed; the survivors (cutting the worktree
from the controller's checkout instead of the base; a refused done-marker commit) each got a
test that kills them.

Real use, main path: a scratch repository built from the eval scaffold, with a bare remote and
a tier 2 record approved on main whose frontmatter lists one task (`shout`, branch
`shout/flag`, `plugin: plugins/change-record`), run with the real agent:

```
$ dispatch docs/changes/2026-11-08-shout.md --red-run 'python3 -m unittest {files}' --worktrees $S/worktrees
dispatch: shout: running the agent in $S/worktrees/shout on shout/flag
turns=15 cost=0.6534017500000001 error=false denied=0
dispatch: shout: the agent's PR description did not start with the Change: line; added it
dispatch: shout: branch=shout/flag commits=3 turns=15 cost=0.6534017500000001 record-check=ok red-check=fail pushed=no body=$S/worktrees/shout.pr-body.md
  red-check: red-check: inconclusive: tests/test_greet.py (exit 1; could not run on the base: ImportError: Failed to import test module: test_greet)
  red-check:     the test did not reach an assertion, so it shows nothing either way; make it fail on the missing behaviour, not on a missing module
  red-check: red-check: no changed test was shown to fail on the base: all 1 inconclusive
  red-check:     make at least one test fail on an assertion about the missing behaviour, or check that the command can run here
dispatch: shout: not pushed; the worktree is kept at $S/worktrees/shout
exit 1
```

The agent followed the loop (a red commit, a green commit, the CLI run as a user, the record's
Outcome filled, 15 turns, 0.65 USD, no denied commands) and `record-check` passed, but
`red-check` gave the one changed test an inconclusive verdict: the test module imports the new
`shout` helper at the top, so on the base it fails on an ImportError before any assertion and
shows nothing. `dispatch` therefore did not push and kept the worktree, which is the gate
working as designed; the branch's program itself works:

```
$ cd $S/worktrees/shout && python3 greet.py --shout Ada && python3 greet.py Ada && python3 -m unittest discover -s tests -t . 2>&1 | tail -1
HELLO, ADA!
Hello, Ada!
OK
```

The first real run, before the fix in Decisions, ended with `fail, the agent made no commits
(turns=39 cost=1.5479957500000001)`: the agent had written the code and tests but was denied
every `python3` and `git` write under `acceptEdits` alone (24 denials). The default command
now allows the Bash tool and the summary line reports `denied=N`.

Error path, in this repository:

```
$ dispatch docs/changes/2026-11-08-outcome-evals.md --dry-run
dispatch: docs/changes/2026-11-08-outcome-evals.md is tier 2 with status 'open' on origin/main; a tier 2 record is dispatched once it is approved there (status: approved), and not once it is done or abandoned
exit 2
$ dispatch docs/changes/2026-11-08-dispatch.md --dry-run
dispatch: docs/changes/2026-11-08-dispatch.md is not on origin/main; a record is dispatched from the base branch, so merge it there first
exit 2
```

Not shipped: opening the pull request from the saved description (left to whoever runs
`dispatch`, with the GitHub tooling they have). Open finding, for the skill rather than the
dispatcher: an agent following the loop can still write a test that imports the new name at
module level, which `red-check` rightly calls inconclusive; the skill's red step could say to
import inside the test or to assert on the program's output, and the eval suite could carry a
case for it.
